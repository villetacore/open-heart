# Мультиплеер OpenHeart

> **Статус: сетевая игра собрана от меню до врагов.** Ядро (`core/`) считает мир, врагов
> и урон; `server/` крутит это в комнате на 20 Гц; клиент подключается из меню, шлёт ввод
> и рисует снапшоты. Дальше — кооперативный геймплей (N2) и список серверов с релеем
> (хвост N2, персонажи и админка из N5). Что именно уже работает — §15, план — §12.
> Дополняет [ARCHITECTURE.md](ARCHITECTURE.md) (как устроен одиночный клиент).

## 1. Что именно строим

Четыре сценария, все должны работать:

| # | Сценарий | Как выглядит для игрока |
|---|---|---|
| 1 | **С другом за минуту** | «Создать игру» → код `K7X2M9` → друг вводит код и заходит. Белый IP не нужен |
| 2 | **Публичный сервер** | Список серверов в меню, зашёл, зарегистрировался, играешь, прогресс хранится там |
| 3 | **Свой сервер за NAT** | Поднял `oh-server`, он сам объявился в списке и работает через релей |
| 4 | **Свой мастер** | Комьюнити поднимает собственный `oh-master`, клиент указывает его адрес |

**Не-цели v1:** PvP-режимы, MMO-масштаб (сотни игроков в одном мире), серьёзный античит,
голосовой чат, кроссплей-магазины, хостинг из веб-сборки. Веб-клиент **как подключающийся** —
цель, но не первого этапа.

## 2. Принцип минимальной инфраструктуры

Осознанное ограничение: **один язык на бэкенде, один файл БД, ноль внешних сервисов.**

| Нужно | Не нужно |
|---|---|
| Go 1.22+, два бинарника | Docker / Kubernetes / Nomad |
| SQLite, один файл на процесс | PostgreSQL, MySQL |
| Реестр серверов в памяти (TTL 60 с) | Redis, очереди, брокеры |
| `CREATE TABLE IF NOT EXISTS` + `PRAGMA user_version` | goose / atlas / миграционные фреймворки |
| systemd-юнит + Caddy для TLS | nginx-зоопарк, service mesh |
| Бэкап = `cp master.db backup/` | pgdump, репликация |

Зависимости Go — только эти, **все чистый Go, без cgo** (важно: бинарник кросс-компилируется
под Linux/Windows/ARM одной командой):

| Пакет | Зачем |
|---|---|
| `github.com/coder/websocket` | WebSocket, и клиентский, и серверный |
| `modernc.org/sqlite` | SQLite без cgo (через `database/sql`) |
| `github.com/tetratelabs/wazero` | запуск wasm-ядра игры (§4) |
| `github.com/hashicorp/yamux` | мультиплексор для релея (§8.3) |
| `golang.org/x/crypto/argon2` | argon2id для паролей |
| stdlib | `net/http`, `crypto/ed25519`, `log/slog`, `encoding/json` |

Всё остальное — стандартная библиотека. Если тянет добавить фреймворк — не надо.

## 3. Топология

```
                     ┌──────────────────── oh-master ────────────────────┐
                     │  реестр публичных серверов (память, TTL 60 c)     │
   ┌─── announce ───▶│  аккаунты + подписанные тикеты (SQLite)           │◀── список ──┐
   │    heartbeat    │  релей: yamux поверх исходящего WSS               │             │
   │                 │  пати-коды                                       │             │
   │                 └──────────────────────┬───────────────────────────┘             │
   │                                        │ туннель                                 │
┌──┴──────────────┐                         │                         ┌───────────────┴─┐
│   oh-server     │◀────────────────────────┘                         │     клиент      │
│  (Go + wasm-    │◀──── прямой WS, если есть белый IP ───────────────│  (Godot + Rust) │
│   ядро игры)    │                                                   └─────────────────┘
│  SQLite: юзеры, │
│  персонажи      │        «Играть с другом» = клиент сам запускает oh-server
└─────────────────┘        дочерним процессом с флагом --relay
```

| Роль | Бинарник | Состояние | Обязателен? |
|---|---|---|---|
| Игровой сервер | `oh-server` | `server.db` (юзеры, персонажи) | да |
| Мастер | `oh-master` | `master.db` (аккаунты, владельцы серверов) | нет — можно играть по прямому IP |
| Клиент | игра | локальные настройки, кеш списка | да |

Мастер **не участвует в игровом тике**. Он нужен для списка серверов, аккаунтов и релея.
Если мастер лежит — уже подключённые сессии продолжают играть, прямой коннект по IP работает.

## 4. Ключевое решение: одна реализация игры на клиенте и сервере

Классическая беда сетевых игр — две разошедшиеся реализации боёвки («на сервере попал,
на клиенте нет»). Мы её не допускаем **по построению**.

Проверка связанности текущего кода с движком показала, что вся симуляционная логика уже
почти свободна от Godot:

| Модуль | Что тянет из Godot сейчас |
|---|---|
| `combat/` (weapon, perk, status) | только `Color` |
| `data/`, `state/` | только `FileAccess` (файловое IO) |
| `worldgen/dungeon.rs`, `nav.rs` | только `Vector3` / `Color` |
| `nodes/` (Game3D, Player, Enemy) | всё — но это слой представления, он и остаётся клиентским |

**План:** выделить крейт `openheart-core` без зависимости от `godot`, положить туда всю
симуляцию и собирать его двумя способами:

```
                  ┌──────────────── openheart-core (Rust) ─────────────────┐
                  │  worldgen (dungeon, nav) · combat (урон, перки,        │
                  │  статусы) · data-модели · sim (авторитетный тик)       │
                  └───────┬───────────────────────────────────┬────────────┘
              cargo dep   │                                   │  --target wasm32
                          ▼                                   ▼
              ┌──────────────────────┐            ┌──────────────────────────┐
              │ openheart.dll (gdext)│            │ core.wasm → wazero       │
              │ рендер, ввод, звук,  │            │ внутри oh-server (Go)    │
              │ предсказание         │            │ авторитетный тик 20 Гц   │
              └──────────────────────┘            └──────────────────────────┘
```

Один и тот же код генерирует данж, считает урон и водит врагов по A* — и на клиенте,
и на сервере. Расхождение формул физически невозможно.

**Роль Go:** сеть, комнаты, тик-луп, аккаунты, персист, валидация, релей, реестр. Go
**не переписывает геймплей** — он платформа вокруг ядра.

Отвергнутые альтернативы:

| Вариант | Почему нет |
|---|---|
| Переписать боёвку и AI на Go | ~3000 строк логики в двух реализациях, вечный рассинхрон |
| Headless Godot как сервер | тяжёлый рантайм, GPU-зависимости, сложный деплой, Go всё равно нужен рядом |
| cgo + `cdylib` вместо wasm | ломает кросс-компиляцию и простоту сборки; wazero даёт песочницу бесплатно |
| Host-authoritative (хост — один из клиентов) | вторая реализация сервера + миграция хоста; embedded `oh-server` решает ту же задачу лучше |

## 5. Разделение авторитета

| Что | Кто решает | Как |
|---|---|---|
| Движение своего игрока | клиент | физика Godot, предсказание; сервер валидирует правдоподобие |
| Позиции врагов, снарядов | **сервер** | нав-грид + A* в ядре, без физдвижка (враги не прыгают — [nav.rs](../client/src/worldgen/nav.rs)) |
| HP, смерть, даун | **сервер** | клиент рисует предсказание, откатывает по подтверждению |
| Попадания | **сервер** | клиент шлёт `HitClaim`, сервер проверяет кулдаун, патроны, дистанцию, LOS |
| Лут, XP, уровни, перки | **сервер** | инстансный лут, роллы на сервере |
| Сид данжа, спавн-таблицы | **сервер** | клиент генерирует тот же данж тем же кодом |
| Квесты, диалоги | **сервер** | прогресс в БД сервера |
| Анимации, звук, FX, HUD | клиент | не реплицируется вообще |

Валидация движения — «мягкая»: сервер не пересчитывает шаг игрока, а проверяет
`|Δpos| <= v_max·Δt·1.25` и что точка лежит в проходимой клетке. Нарушение → коррекция
(возврат к последней валидной позиции), при систематике → кик. Для кооп-PvE этого достаточно:
читер портит игру только своей пати.

## 6. Транспорт и протокол

### 6.1 Транспорт

**WebSocket over TLS** — единственный выбор, который переживает всё сразу: веб-сборку
(в браузере нет raw UDP), корпоративные фаерволы (порт 443), релей (§8.3) и наличие
`WebSocketPeer` в gdext. TCP-джиттер для кооп-PvE на 20 Гц терпим.

UDP/QUIC — этап N7, только для нативных клиентов и только если упрёмся в задержки.

### 6.2 Кодек

v1 — **JSON**: у нас уже везде `serde`, протокол дебажится глазами. Переход на бинарь
(`postcard` ↔ Go-кодек) — этап N7, когда сообщения устаканятся и трафик станет заметен.
Схема — единственный источник правды в `protocol/schema.md`, структуры пишутся руками
с обеих сторон плюс тест на совместимость.

### 6.3 Сообщения

Клиент → сервер:

| Сообщение | Поля | Частота |
|---|---|---|
| `Hello` | `protocol, game_version, preset_id, content_hash, auth{mode, ticket\|login\|nickname}` | при коннекте |
| `Input` | `tick, move[2], yaw, pitch, buttons, pos, vel, on_floor` | 30 Гц |
| `Fire` | `tick, weapon, origin, dir, secondary` | по событию |
| `HitClaim` | `tick, weapon, target_id, hit_pos, part` | по событию |
| `Interact` | `target_id, kind` (NPC, дверь, портал, подъём) | по событию |
| `Cmd` | `kind, args` (сменить оружие, взять перк, экипировать, войти в делв) | по событию |
| `Chat` | `text` | по событию |
| `Ping` | `t` | 1 Гц |

Сервер → клиент:

| Сообщение | Поля |
|---|---|
| `Welcome` | `peer_id, tick, preset_id, content_hash, world{kind, seed, depth}, players[]` |
| `Snapshot` | `tick, ack_input, players[], enemies[], projectiles[], items[]` — дельта к последнему ack |
| `Event` | `Damage / EnemyDied / Loot / Xp / LevelUp / QuestUpdate / Downed / Revived / Join / Leave / Chat / WorldLoad` |
| `Reject` | `reason` (версия, content_hash, авторизация, бан, сервер полон) |
| `Pong` | `t` |

Запись сущности в снапшоте: `id:u16, kind:u8, pos:3×i16 (квант 1/64 м), yaw:u8, hp:u8,
flags:u8` ≈ **11 байт**. 60 врагов + 4 игрока ≈ 700 Б на снапшот.

### 6.4 Тайминги

| Параметр | Значение | Почему |
|---|---|---|
| Тик сервера | 20 Гц (50 мс) | достаточно для DOOM-боёвки с хитсканом на клиенте |
| Отправка инпута | 30 Гц | плотнее тика, сервер берёт последний |
| Буфер интерполяции чужих | 100 мс | два снапшота запаса |
| Таймаут соединения | 15 с | слот держится под реконнект 60 с |

## 7. `oh-server` — игровой сервер

### 7.1 Устройство

```
main → config → store(SQLite) → wasm(core.wasm) → hub
                                                   ├── room #0  хаб   (горутина, тик 20 Гц)
                                                   ├── room #1  делв  (горутина, тик 20 Гц)
                                                   └── ...
      ws-listener → conn(горутина чтения) ─chan─▶ room.inbox
                    conn(горутина записи) ◀─chan─ room.outbox
```

**Комната = одна горутина + каналы.** Игровое состояние живёт в линейной памяти wasm,
никто, кроме тика этой комнаты, к нему не обращается — ноль мьютексов на геймплее.
Каждая комната — отдельный инстанс wasm-модуля (wazero компилирует модуль один раз,
инстансы дешёвые).

Хаб — комната №0, общая. Делв — комната на пати, создаётся по `Cmd{enter_delve}` и умирает
после завершения забега (с задержкой на реконнект, см. §13.5).

### 7.2 ABI ядра

Вызовы крупноблочные — раз в тик, а не на сущность:

```
sim_new(cfg_ptr, len) -> handle          // пресет, сид, режим, состав пати
sim_tick(handle, dt, inputs_ptr, len)    // -> snapshot_ptr, events_ptr
sim_cmd(handle, msg_ptr, len)            // -> events_ptr
sim_save(handle) -> blob                 // персист состояния комнаты
sim_load(blob_ptr, len) -> handle
```

Go отвечает за приём инпутов, сборку батча, вызов `sim_tick`, дельта-кодирование снапшота,
рассылку и применение событий к БД.

### 7.3 SQLite

```sql
PRAGMA journal_mode=WAL;

CREATE TABLE IF NOT EXISTS users (
  id           INTEGER PRIMARY KEY,
  account_ref  TEXT UNIQUE NOT NULL,   -- 'master:1234' | 'local:vasya' | 'guest:<uuid>'
  nickname     TEXT NOT NULL,
  pass_hash    TEXT,                   -- argon2id, только для local
  role         TEXT NOT NULL DEFAULT 'player',   -- player | mod | admin
  created_at   INTEGER NOT NULL,
  last_seen    INTEGER
);

CREATE TABLE IF NOT EXISTS characters (
  id         INTEGER PRIMARY KEY,
  user_id    INTEGER NOT NULL REFERENCES users(id),
  preset     TEXT NOT NULL,
  name       TEXT NOT NULL,
  class_id   TEXT, spec_id TEXT, level INTEGER, xp INTEGER,
  save_ver   INTEGER NOT NULL,
  save_json  TEXT NOT NULL,            -- ровно то, что пишет client/src/state/save.rs
  updated_at INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS bans (
  account_ref TEXT PRIMARY KEY, reason TEXT, until INTEGER, by TEXT
);

CREATE TABLE IF NOT EXISTS kv (key TEXT PRIMARY KEY, value TEXT);
```

`save_json` — существующий формат сейва целиком, без переизобретения: в [save.rs](../client/src/state/save.rs)
уже везде `#[serde(default)]`, миграции переживёт. Автосейв — раз в 30 с и при выходе игрока.

### 7.4 Конфиг

Один TOML рядом с бинарником, всё переопределяется флагами и env:

```toml
name        = "Неоновый квартал #1"
motd        = "PvE кооп, 4 слота"
preset      = "neon_heart"
max_players = 16
party_size  = 4
auth        = "master"        # master | local | open
password    = ""              # пароль на вход, опционально
listen      = ":7777"
master      = "https://master.openheart.example"
public      = true            # объявляться в списке
relay       = false           # true — если нет белого IP
db          = "server.db"
```

## 8. `oh-master` — реестр, аккаунты, релей

### 8.1 HTTP API

```
POST /v1/auth/register      {login, password, email?}      -> {account_id}
POST /v1/auth/login         {login, password}              -> {refresh_token}
POST /v1/auth/ticket        {refresh_token, server_id}     -> {ticket}    # ed25519, TTL 60 c
GET  /v1/auth/pubkey                                       -> {pubkey}    # для офлайн-проверки

POST /v1/servers/register   {name, ...} + Bearer           -> {server_id, server_secret}
POST /v1/servers/announce   {server_id, ...} + secret      -> {ok, relay_endpoint?}
GET  /v1/servers?preset=&protocol=&region=                 -> [{...}]

POST /v1/party/create       {server_id} + secret           -> {code, expires_at}
GET  /v1/party/{code}                                      -> {endpoint}
```

`announce` — раз в 20 с, запись живёт 60 с. **Реестр держим в памяти** (`map[string]entry`
под мьютексом): при рестарте мастера сервера сами переанонсятся через 20 с, писать в БД нечего.

Поля анонса: `name, motd, region, players, max_players, preset_id, content_hash,
game_version, protocol_version, mode, passworded, auth_mode, endpoint`.

`content_hash` (sha256 по JSON пресета) — не косметика: пресет и есть игра, при расхождении
у одного игрока дробовик на 30 урона, у другого на 45. Клиент по умолчанию прячет
несовместимые сервера.

### 8.2 SQLite

```sql
CREATE TABLE IF NOT EXISTS accounts (
  id INTEGER PRIMARY KEY, login TEXT UNIQUE NOT NULL, pass_hash TEXT NOT NULL,
  email TEXT, created_at INTEGER NOT NULL, last_seen INTEGER, banned INTEGER DEFAULT 0
);
CREATE TABLE IF NOT EXISTS refresh_tokens (
  token_hash TEXT PRIMARY KEY, account_id INTEGER NOT NULL, expires_at INTEGER NOT NULL
);
CREATE TABLE IF NOT EXISTS servers (
  id TEXT PRIMARY KEY, owner_id INTEGER NOT NULL, name TEXT,
  secret_hash TEXT NOT NULL, created_at INTEGER, listed INTEGER DEFAULT 1
);
```

Живой список серверов и активные пати-коды — только в памяти.

### 8.3 Релей: хостинг без белого IP

Никакой NAT-магии, всё на готовых кирпичах:

1. `oh-server -relay` делает **исходящее** WSS-соединение на `/v1/relay/connect`
   (аутентификация — та же пара `server_id` + `secret`, что и для анонса) и держит его открытым.
   Обрыв — реконнект с бэкоффом 2 → 60 с.
2. Поверх — **yamux**: звонивший хост становится клиентом мультиплексора, мастер — сервером,
   поэтому стримы открывает мастер. Каждый входящий игрок = новый стрим.
3. Мастер выдаёт публичную точку `wss://master/j/<token>`; игрок коннектится туда, мастер
   открывает стрим к хосту и перекладывает байты.

Внутри стрима сообщения идут кадрами `[4 байта длины BE][тело]`: стрим байтовый, игровой
протокол — сообщения, границы между ними терять нельзя. Предел кадра — те же 64 КиБ, что и у
прямого WebSocket: туннель не должен пропускать то, что прямой канал отверг бы.

Первым кадром нового стрима мастер сообщает хосту адрес игрока — через туннель настоящий адрес
иначе не виден, а он нужен и в логах, и в рейт-лимитах. Дальше мастер игровой протокол не
разбирает вовсе.

Со стороны комнаты разницы нет: `wire.Conn` — интерфейс, у него две реализации, прямой
`wire.WSConn` и туннельный `relay.StreamConn`. Сессия (`handshake`, смена комнат, выход)
одна на оба случая.

Релейный сервер **не знает своей точки входа** — её выдаёт мастер. Поэтому анонс и пати-код
ждут поднятого туннеля: до этого мастер отвечает `412` и подставлять в список нечего.

Почему релей, а не hole punching, с самого начала:

| | Релей | UDP hole punching |
|---|---|---|
| CGNAT, симметричный NAT | работает | 20–30% провалов |
| Корпоративный фаервол | работает (443/TLS) | нет |
| Веб-клиент | работает | невозможно |
| Свой протокол писать | не надо (yamux) | надо |
| Цена | трафик мастера + RTT | почти ноль |

Punching — этап N7 как оптимизация для нативных клиентов; мастер уже рандеву-точка, а релей
останется фолбэком. Пати-код `K7X2M9` — человекочитаемый алиас релей-токена.

### 8.4 Игра с другом: хост без аккаунта

«Позвать друга» не должно упираться в регистрацию, поэтому у мастера есть
`POST /v1/party/host`: он выдаёт **временную личность хоста** — такую же пару
`server_id` + `secret`, но без владельца и с жизнью в 12 часов. Взамен такой хост
не попадает в список серверов: анонс в реестр требует аккаунта, а личность из
`party_hosts` его не имеет. Ему доступны ровно две вещи — релей и пати-код.

Дальше всё как у обычного сервера: `oh-server -party` берёт личность, поднимает
туннель, просит у мастера код и пишет **файл состояния** для запустившего его
клиента:

```json
{ "ready": true, "listen": "127.0.0.1:7788", "code": "K7X2M9", "preset": "core" }
```

Через stdout это не передать — клиент запускает сервер фоновым процессом, а
читать его вывод построчно из движка неудобно. Файл проще: клиент ждёт, пока он
появится, и читает целиком.

Хозяин заходит к себе **напрямую** на `127.0.0.1`: гонять свой же трафик через
релей мастера незачем. Друзья заходят по коду. Брошенный хост выключается сам:
`-party` включает `-idle-exit 5m`, иначе после каждой игры на машине оставался бы
живой сервер с открытым туннелем.

**Бюджет релея:** 4 игрока × 20 Гц × ~700 Б ≈ 56 КБ/с на комнату в одну сторону. VPS
с каналом 100 Мбит держит ~200 комнат. Квота трафика на комнату и лимит комнат на аккаунт —
обязательны с первого дня, иначе релей превращается в бесплатный туннель-сервис для чужих нужд.
Сейчас стоит первая половина: не больше 32 одновременных стримов на туннель, переподключение
сервера закрывает его прежний туннель. Счётчика байтов ещё нет — он на N6.

## 9. Клиент

| Слой | Где | Что делает |
|---|---|---|
| Сетевой | новый `client/src/net/` | `WebSocketPeer`, кодек, очереди, реконнект |
| Предсказание | `Player` + `net` | свой игрок ходит локально, сверяется со `Snapshot`, мягкая коррекция |
| Интерполяция | `net` + `Game3D` | чужие игроки и враги — по буферу 100 мс |
| UI | `main_menu.rs` | новые экраны: логин, список серверов, создать игру, лобби пати |

Новые экраны меню: **Играть с другом** (создать / ввести код), **Серверы** (список из мастера,
избранное, прямой IP, история), **Аккаунт** (логин и регистрация на мастере).

Логика «создать игру»: клиент запускает `oh-server --embedded --relay --preset <текущий>`
дочерним процессом, ждёт код от мастера и коннектится на `127.0.0.1`. Один и тот же бинарник
сервера работает и как дедик, и как игра вдвоём — второй реализации хоста не существует.
Веб-сборка процессы не форкает: в вебе доступно только подключение.

## 10. Аккаунты и безопасность

Сервер объявляет `auth_mode`, клиент показывает соответствующий экран:

| Режим | Кто проверяет | Для чего |
|---|---|---|
| `master` | подпись мастера, офлайн | публичные сервера |
| `local` | сам сервер, таблица `users` | приватные комьюнити |
| `open` | никто, только ник | игра с другом |

**Флоу `master` (модель session-тикетов):**

```
клиент ──login(логин, пароль)──▶ мастер        # пароль уходит ТОЛЬКО мастеру
клиент ◀──refresh_token─────────
клиент ──ticket(server_id)─────▶ мастер
клиент ◀──ticket{account_id, nickname, aud: server_id, exp:+60s, sig(ed25519)}
клиент ──Hello{ticket}─────────▶ игровой сервер
                                 сервер проверяет подпись публичным ключом мастера, офлайн
```

Почему так, а не «логин-пароль на каждом сервере»: сервера в списке поднимают посторонние
люди. Если бы игроки вводили там мастер-пароль, любой владелец сервера собирал бы чужие
аккаунты. Игровой сервер видит только подписанный тикет и никогда — пароль.

Правила, которые не обсуждаются:

- Пароли — **argon2id** (`time=3, memory=64MB, threads=4`), соль на запись. Никакого MD5/SHA.
- TLS обязателен для мастера и публичных серверов (Caddy перед процессом либо `--tls`).
- Тикет одноразовый, `aud` привязан к `server_id`, TTL 60 с — украденный бесполезен.
- Рейт-лимит на `login`/`register` (10/мин на IP), задержка после неудачных попыток.
- E-mail опционален, только для восстановления, в списке серверов не светится.
- Баны по `account_ref` — на стороне сервера; мастер банит только листинг, не игру.
- Гостевой вход даёт `guest:<uuid>`, привязанный к машине; прогресс не переносится.

## 11. Геймплей: что придётся переделать

Главная работа не в сети, а здесь. Одиночная игра построена на допущениях, которые
в кооперативе ломаются:

| # | Как сейчас | Что делаем |
|---|---|---|
| 1 | Диалоги/инвентарь/перки останавливают мир (`Mode::*` в [game/mod.rs](../client/src/nodes/game/mod.rs)) | non-blocking UI: мир продолжает жить, в инвентаре ты уязвим; тяжёлые экраны — только в безопасной зоне хаба |
| 2 | ✅ `Enemy::set_player()` — ровно одна цель | **таблица угрозы** (`core/src/sim/enemy.rs`): цель выбирается по нанесённому урону плюс небольшой вклад близости; урон забывается со временем, смена цели требует запаса, лежачих не добивают |
| 3 | ✅ Смерть = `Mode::Dead` = конец забега | **даун и ревайв напарником**: 5 с удержания «использовать» рядом, подъём на 30 % здоровья; 45 с кровотечения, потом игрок выбывает; `wipe` — только когда легли все |
| 4 | ✅ Лут падает в мир общей кучей | **инстансный лут**: с каждого врага свой бросок каждому живому игроку; чужие предметы сервер даже не шлёт — их нельзя ни увидеть, ни вычитать из трафика |
| 5 | ✅ Баланс на одного | скейлинг: врагов ×(1 + 0.6·(n−1)), HP ×(1 + 0.35·(n−1)); **урон врагов не масштабируется** — это отдельный тест, потому что первая реализация его случайно раздувала |
| 6 | ✅ Хаб и делв одинаково локальны | хаб — общая комната сервера; делв — **отдельный инстанс** (`server/internal/room/manager.go`): создаётся по `cmd{enter_delve}`, адресуется по ведущему (`owner`), закрывается через минуту после того, как все ушли |
| 7 | Сейв — локальный файл | персонаж живёт на сервере, где создан; локальные персонажи — только на `open`-серверах |
| 8 | Квесты одиночные | kill/collect/clear — общий зачёт всем в пати в радиусе 50 м; сюжетные цепочки — персональный прогресс |
| 9 | 8 комбо-синергий перков | ревизия баланса: ауры и стаки на четверых могут ломаться; часть перков пометить «не стакается в пати» |
| 10 | Сид от `game_time.to_bits()` ([environment.rs:557](../client/src/nodes/game/environment.rs:557)) | любой геймплейный сид приходит от сервера; локального времени в сидах нет |
| 11 | Хитскан бьёт мгновенно и локально | лаг-компенсация: сервер проверяет попадание по позициям врагов «на тик клиента» (история 500 мс) |
| 12 | Пикапы-сердца общие | остаются общими (кооперативный ресурс), но с персональным кулдауном 1 с, чтобы не было гонки |

## 13. Открытые вопросы

Решить до N2 — они меняют дизайн, а не реализацию:

1. **Прогрессия.** Персонаж принадлежит серверу (как в MMO, защищено от подкруток) или это
   локальный файл, который несёшь на любой сервер (как открытые персонажи D2, но читерский)?
   Черновой ответ: серверный на `master`/`local`, локальный разрешён на `open`.
2. **Хаб.** Общий социальный на 16 игроков или тоже инстанс на пати? Общий даёт «живой мир»
   и нагрузку, инстанс проще. Черновой ответ: общий, но боёвки в хабе нет.
3. **Размер пати.** 4 (баланс, скейлинг, читаемость экрана) или больше? Черновой ответ: 4.
4. **Что делает игрок, пока его пати в делве** — ждёт в хабе, смотрит за товарищами или
   уходит вторым забегом?
5. **Сколько живёт делв-инстанс после выхода всех** — можно ли реконнектнуться в тот же
   забег и сколько времени?

| `oh-server` | WS, комната, тик 20 Гц, SQLite, три режима auth, анонс в мастер |

| Проверка движения | телепорт отклоняется ядром (тест `teleport_is_rejected`) |
| `oh-master` | регистрация, логин, refresh, ed25519-тикеты, реестр, пати-коды, рейт-лимит |
| `oh-probe` | бот-клиент: hello → welcome → ввод 30 Гц → снапшоты |
| Список серверов | анонс сервера появляется в `GET /v1/servers`, фильтр по `content_hash` отсекает несовместимые |

| Таблица угрозы | враг переключается на того, кто наносит урон; угроза тает, мелкие царапины цель не меняют |
| Инстансный лут | каждому свой бросок с врага, чужое не приходит по сети; подбор, срок жизни и события `loot`/`pickup` |
| Скейлинг пати | врагов больше и они крепче, урон не растёт; пересчёт идёт по фактическому составу забега — зашёл товарищ, и врагов стало 60 вместо 38 |
| Даун и ревайв | упавший ждёт помощи, товарищ поднимает удержанием кнопки, кровотечение 45 с; забег провален только при полном вайпе — проверено и тестами, и живым прогоном бота |
| Релей | сервер без белого IP держит исходящий туннель к мастеру; мастер выдаёт `ws://master/j/<token>`, и по этому адресу игрок заходит как на обычный сервер |
| Пати-код через релей | `POST /v1/party/create` у релейного сервера отдаёт код, который резолвится в точку входа туннеля |
| Кооп сквозь туннель | два бота зашли по одному коду, ушли в общий забег, били врагов и подбирали свой лут — всё через один туннель, разными стримами |
| Список серверов в клиенте | меню спрашивает мастера и показывает игры: заполненность, регион, релей, чужая версия; несовместимые видно до клика, а не по отказу сервера |
| Вход по пати-коду | код от друга резолвится у мастера и уводит прямо в его игру, адрес сервера знать не нужно |
| Создать игру с другом | кнопка в меню поднимает `oh-server -party` дочерним процессом: он берёт у мастера временную личность без аккаунта, поднимает туннель и возвращает код |
| Брошенный хост убирает себя | сервер с `-party` выключается после пяти минут без игроков, а мастер чистит протухшие личности при старте |
| Клиент следует за миром сервера | `welcome` несёт `kind`/`seed`/`depth`, и клиент строит тот же забег; раньше можно было ходить по хабу, пока сервер считал данж |
| Соединение не рвётся на паузе | пока игрок выбирает класс или читает диалог, клиент шлёт пинг: сервер отключает молчащих через 15 с |
| Крафт | рецепты в пресете, правила в ядре, экран по клавише `C` |
| Экран подключения | в меню появилась кнопка «Подключиться»: адрес сервера вводится и запоминается в настройках |
| Сверка данных пресета | клиент считает `content_hash` (sha256 по файлам пресета) — Rust-тест сверяет результат с Go-эталоном; с чужим набором JSON сервер не пускает |
| Коррекция позиции | мелкое расхождение подтягивается плавно (6 м/с), крупное — телепортом |
| Клиент говорит с сервером | `client/src/net/`: сессия с тестами, сокет на `WebSocketPeer`, ввод 30 Гц, снапшоты в узлы, заявки о попаданиях |
| Совместимость Rust ↔ Go | образцы сообщений в `protocol/fixtures/` разбирают обе стороны своими тестами |
| Враги живут на сервере | делв строится по плану данжа, враги берутся из пресета, ходят по A*, бьют игрока; всё внутри `core.wasm` |
| Урон проверяется сервером | заявка клиента о попадании отбраковывается по темпу стрельбы и дальности, урон считается с резистами |
| Правила игры в ядре | боёвка, перки, статусы, модели контента, прогресс, навигация, формат карты, план данжа — 9400 строк без движка |
| Ввод клиента развязан | `Player` двигается по `PlayerInput`; локальный собирает её сам, чужой получит по сети |
| Игроки как мапа | `Game3D.players: HashMap<PeerId, …>` + `local_peer`; одиночная игра — частный случай на одного |
| Стабильные id врагов | `Enemy::entity_id`, выдаётся при спавне; поиск через `enemy_by_id` |
| Хуки хоста | ядро пишет предупреждения и читает файлы через хук: в клиенте это движок, на сервере — файловая система |
| Тесты | 143 (117 Rust + 26 Go): `core` — пресеты, данж, враги, урон, протокол и фикстуры; `client` — сетевая сессия и разбор ответов мастера; `server` — auth, proto, реестр, комнаты, забеги, кадры и туннель релея |
| Структура репозитория | `core/`, `client/`, `server/`, `protocol/`, `game/`, `scripts/` — по смыслу, а не по языкам; сборка клиента — `cargo build -p openheart` |
| CI | job «Go: build + vet + test, core.wasm» + `cargo … --workspace`, сборки платформ пришпилены к `-p openheart` |

Смоук-проверка целиком:

```bash
./scripts/core-wasm.sh          # соберёт ядро и положит его в server/core.wasm
cd server && go run ./cmd/oh-server -listen 127.0.0.1:7777 \
    -preset core -presets ../game/presets -auth open -core core.wasm
# в другом терминале:
go run ./cmd/oh-probe -addr ws://127.0.0.1:7777/ws -nick bot1 -seconds 5
```

Через релей (сервер вообще не слушает снаружи):

```bash
OH_PUBLIC_URL=http://127.0.0.1:8899 go run ./cmd/oh-master -listen 127.0.0.1:8899
# server_id и secret получить один раз: POST /v1/servers/register с Bearer-токеном аккаунта
OH_SERVER_ID=… OH_SECRET=… go run ./cmd/oh-server -master http://127.0.0.1:8899 \
    -preset core -presets ../game/presets -auth open -core core.wasm -public -relay
# точка входа появится в GET /v1/servers как ws://127.0.0.1:8899/j/<token>
go run ./cmd/oh-probe -addr ws://127.0.0.1:8899/j/<token> -nick bot1 -seconds 5
```

Известные ограничения:

* внутри `core.wasm` нет файловой системы, поэтому сервер играет на **встроенных** данных
  core-пресета (`include_str!`); для чужих пресетов нужен вызов ABI, которым хост передаёт
  файлы в ядро перед `sim_new`;
* полноценной перемотки предсказания не будет в текущем виде: движение считает
  `move_and_slide` движка, переиграть его назад нельзя — поэтому расхождение
  сглаживается, а не откатывается;
* чужие игроки рисуются простым биллбордом, дельта-снапшотов нет (каждый тик уходит полным).

Чего ещё нет: избранного и истории серверов, персонажей в БД сервера, дельта-снапшотов
(пока каждый тик уходит полным), счётчика трафика релея, строительства, обучения весов для ИИ.
