# Разработка и проверка

[Навигация](README.md) · Команды выполняются из корня репозитория, если не указано другое.

## Зависимости и запуск

Нужны Rust/Cargo, Godot 4.7 с поддержкой GDExtension и инструменты компиляции платформы. Go нужен для сервера, Python — для скриптов контента. Версии зависимостей закреплены в Cargo.lock и go.mod; установку инструментов сверять с ними и CI.

Windows:

```powershell
.\scripts\run.ps1 -Engine 'C:\path\to\godot.exe' -Game
```

Без `-Game` скрипт открывает редактор. Он собирает `openheart` и копирует DLL в `game/bin`. Закрыть использующую DLL игру перед пересборкой. Не путать успешный `cargo build` с обновлённой DLL, уже загруженной Godot.

Терминал:

```powershell
cargo run -p openheart-terminal -- --offline
```

Сервер и WASM: [инструкции сервера](../../server/README.md), [сетевые границы](NETWORKING.md). Для Linux/macOS есть скрипты в [scripts](../../scripts/); параметры экспорта сверять с [export_presets.cfg](../../game/export_presets.cfg).

## Базовые проверки

```powershell
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
python tools/audit_project.py
```

Из каталога `server`:

```powershell
go test ./...
go vet ./...
```

Тесты данных, чистой симуляции и клиента не запускают полный пользовательский маршрут Godot. Два интеграционных теста терминала по умолчанию игнорируются: им нужны реальные сервер/WASM и переменные `OH_TEST_SERVER`, `OH_TEST_CORE`. Не включать их в число пройденных.

## Проверка в движке

В [game/tools](../../game/tools/) находятся runtime-проверки. Для проверки нового эпизода на Windows используйте отдельные пользовательские данные, собранную DLL и импортированные ресурсы:

```powershell
$env:APPDATA = Join-Path (Get-Location) 'target/evening-qa-user'
& 'C:\path\to\godot.exe' --headless --path game --script res://tools/evening_smoke.gd -- --creative
```

Запускать в отдельном терминале: переменная действует на последующие процессы этой сессии. Smoke проверяет условия, награды, повторный финал, ресурсы и отсутствие записи кампании. Графический запуск без `--headless` дополнительно сохраняет кадр в `target/evening-review.png`; его нужно осмотреть. Headless не проверяет внешний вид.

После существенного изменения геймплея пройти вручную: новая игра → класс → NPC/задание → данж → бой/награда → возвращение → сдача → сохранение и перезапуск. Для сети добавить два клиента, подключение/отключение и восстановление состояния. Для экспорта повторить маршрут из собранного пакета без рабочего каталога разработчика.

## Типичные причины расхождений

| Симптом | Что проверить |
|---|---|
| JSON изменён, игра старая | Одноимённый RON имеет больший приоритет; синхронизировать нужный stem |
| Тест hash упал после редактора | Сначала diff: сериализация/пробелы тоже влияют на hash |
| DLL не копируется | Запущенный Godot удерживает библиотеку |
| Картинка есть на диске, но не в игре | Путь, регистр, импорт, `.tres`, регион атласа, ссылка из текущей сцены |
| Пользовательский пресет не перекрывает встроенный | При совпадающем ID выбирается ресурсный пресет; использовать новый ID |
| Сервер запустился, боя нет | Проверить загрузку `core.wasm`: stub не реализует полный бой |
| Старое сохранение меняет результат теста | Изолировать пользовательский каталог, не удалять личный save |

## CI и выпуск

[Pipeline](../../.github/workflows/pipeline.yml) описывает автоматические проверки, smoke и платформенные сборки. Наличие шага в YAML не означает, что последний запуск успешно прошёл. В отчёте указывать конкретную проверенную сборку и фактический результат.

Перед релизом: проверить чистую установку, экспорт ресурсов, миграцию сохранения, разрешения экрана, обе локализации и заявленные сетевые режимы. У тестов нет автоматического ответа на вопросы темпа, понятности и удовольствия от боя — для них нужны плейтесты.

Результаты проверки на 27.09.2026 и ограничения — в [аудите](PROJECT_AUDIT.md).
